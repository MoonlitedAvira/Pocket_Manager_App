# Технический дизайн-документ: Android-клиент Pocket Manager (MVP)

## 1. Общая архитектурная концепция

Приложение построено на основе паттерна **MVVM (Model-View-ViewModel)** и следует подходу **Single Activity Architecture** (Архитектура с одной Activity).
* **Декларативный UI:** Весь пользовательский интерфейс написан с использованием современного фреймворка **Jetpack Compose**.
* **Асинхронность:** Для работы с фоновыми задачами и сетевыми запросами используются **Kotlin Coroutines**.
* **Управление состояниями:** Передача данных от бизнес-логики в UI осуществляется с помощью реактивных потоков **StateFlow**.
* **Навигация:** Используется **Navigation Compose** с типизированной маршрутизацией (Type-safe routing) на основе `kotlinx.serialization`.

## 2. Структура проекта и ответственность слоев

Проект логически разделен на несколько слоев.

### 2.1. Слой данных (Data Layer)
Отвечает за взаимодействие с внешним миром (сервером) и описывает контракты обмена данными.
* **`Models.kt` (Data Transfer Objects):** Описывает структуру данных (сущности), которые приходят от сервера и отправляются ему. Используется библиотека `kotlinx.serialization` для преобразования JSON в объекты Kotlin.
* **`ApiService.kt`:** Интерфейс библиотеки Retrofit, который описывает все доступные серверные эндпоинты (`/auth/login`, `/tasks`, `/pomodoro` и т.д.) и типы HTTP-запросов (GET, POST, PUT, DELETE).
* **`ApiClient.kt`:** Фабрика настройки сетевого клиента. Содержит настройку `OkHttpClient`. Ключевая особенность: наличие `authInterceptor`, который автоматически "перехватывает" каждый исходящий запрос и подставляет в заголовок `Authorization` текущий Bearer-токен пользователя.

### 2.2. Утилиты и безопасность (Utils)
* **`SessionManager.kt`:** Класс, отвечающий за сессию пользователя. Для хранения токена авторизации используется `EncryptedSharedPreferences`. Это обеспечивает шифрование данных на уровне файловой системы устройства (AES256), защищая токен от извлечения злоумышленниками.

### 2.3. Слой представления (Presentation / ViewModels)
Связующее звено между данными и пользовательским интерфейсом. `ViewModels` переживают поворот экрана и хранят актуальное состояние.
* **`LoginViewModel`:** Управляет процессом входа и регистрации. Имеет конечный автомат состояний `LoginState` (`Idle`, `Loading`, `Success`, `Error`), на который реагирует UI.
* **`TaskViewModel`:** Отвечает за загрузку списка задач, добавление, редактирование и удаление (CRUD операции). Хранит загруженный список в `StateFlow`.
* **`PomodoroViewModel`:** Управляет логикой таймера фокуса. Содержит фоновую корутину, отсчитывающую время (`delay(1000)`), и автоматически отправляет результаты на сервер при завершении сессии.
* **`SanViewModel`:** Управляет прохождением теста САН и получением истории (статистики) результатов.
* *(Вспомогательное)* **Фабрики (`*Factory`)**: Так как во ViewModels нужно передавать параметры (например, `ApiService`), используются реализации `ViewModelProvider.Factory` для ручного внедрения зависимостей (Dependency Injection).

### 2.4. Пользовательский интерфейс (UI Layer)
Отвечает исключительно за отображение данных (State) и проброс пользовательских действий (Intents) во ViewModel.
* **`MainActivity.kt`:** Точка входа. Здесь происходит базовая инициализация сервисов (`SessionManager`, `ApiClient`), создаются фабрики, настраивается `NavHost` для навигации и боковое меню `ModalNavigationDrawer`. Также здесь определяется, куда попадет пользователь при запуске: на экран входа (если токена нет) или на главный экран (если токен есть).
* **Пакет `ui/screens/`:** Набор Composable-функций для отрисовки экранов. Экраны изолированы от логики: они лишь принимают `ViewModel`, подписываются на состояния (например, `val tasks by viewModel.tasks.collectAsState()`) и вызывают методы ViewModel (например, `viewModel.completeTask(id)`) при нажатии на кнопки.
* **Пакет `ui/theme/`:** Централизованное управление цветами (`Color.kt`), типографикой (`Type.kt`) и поддержкой темной/светлой темы приложения (`Theme.kt`) в соответствии с Material Design 3.

## 3. Схема взаимодействия компонентов (Data Flow)

Архитектура работает по принципу **однонаправленного потока данных (Unidirectional Data Flow)**.

Рассмотрим жизненный цикл данных на примере работы с задачами:

1.  **Действие пользователя (Action):** Пользователь открывает экран `TaskListScreen`.
2.  **Запрос данных:** `TaskListScreen` инициализируется и `TaskViewModel` в блоке `init` запускает метод `fetchTasks()`.
3.  **Сетевой слой:** ViewModel запускает корутину и обращается к `apiService.getTasks()`.
4.  **Перехват запроса:** `ApiClient` ловит запрос, извлекает JWT-токен из `SessionManager` и прикрепляет его к HTTP-заголовку.
5.  **Получение ответа:** Retrofit делает запрос на сервер, получает JSON и десериализует его в список объектов `TaskResponse`.
6.  **Обновление состояния (State Mutation):** `TaskViewModel` обновляет значение `_tasks.value` (StateFlow) полученным списком.
7.  **Перерисовка (Recomposition):** `TaskListScreen`, подписанный на `tasks`, автоматически реагирует на изменение состояния и перерисовывает `LazyColumn` (список) с новыми данными.

## 4. Направление развития (Архитектурный долг для Этапа 2)

Текущая реализация полностью покрывает требования MVP (Этап 1). Для подготовки приложения к релизу (Этап 2 и 3) в архитектуру планируется внести следующие изменения:
1.  **Локальное кэширование (Офлайн-режим):** Внедрение библиотеки **Room** (SQLite) в слой данных для хранения задач локально и реализации паттерна "Repository" (Единый источник истины).
2.  **Внедрение зависимостей (DI):** Замена ручного создания фабрик в `MainActivity` на фреймворк **Dagger Hilt** для автоматического связывания компонентов.
3.  **Обработка сетевых ошибок:** Внедрение обертки `Result<T>` (Success/Error) на уровне сетевого слоя для безопасной обработки обрывов связи без падения (crash) приложения.
